Estándar Técnico: API-First

Adopción y Guía de Uso de OpenAPI Generator

1. Introducción

Este documento establece el estándar para la construcción de APIs RESTful en nuestro ecosistema de microservicios, consolidando el enfoque API-First. Mediante el uso de OpenAPI Generator, automatizamos la creación de contratos, DTOs y clientes, garantizando una arquitectura desacoplada y sincronizada bajo los principios de la Arquitectura Hexagonal.

2. Flujo de Trabajo (Metodología SPECT)

  1. Diseño del Contrato (S - Specification): Siguiendo el flujo SPECT, definimos primero el archivo openapi.yaml. Este contrato es la "Única Fuente de Verdad" (SSoT) y debe ser aprobado antes de iniciar cualquier implementación.
  2. Generación de Código: Durante la compilación (Gradle), el generador crea:
    • Interfaces de Controladores (Server Stubs) con el Delegate Pattern.
    • DTOs con validaciones Jakarta/Bean Validation (@NotNull, @Size, etc.).
    • Clientes de API (SDKs internos) para comunicación entre microservicios.
  3. Implementación del Delegado: Se implementa el *DelegateImpl donde se realiza el mapeo entre DTOs y Modelos de Dominio usando MapStruct.
  4. Orquestación: El delegado llama al puerto de entrada (UseCase) correspondiente en la capa de aplicación.

3. Ventajas Principales

🚀 Productividad

  • Cero DTOs manuales: Se acabó escribir clases repetitivas y sus mappers básicos.
  • Contratos inmediatos: Los equipos de Frontend y otros Microservicios pueden empezar a trabajar con el contrato antes de que la lógica esté implementada.
  • Reducción de errores: Se eliminan los errores de "typo" en nombres de campos o tipos de datos.

🛡️ Calidad y Consistencia

  • Garantía de Firma: Los clientes siempre consumen la versión exacta que el servidor expone.
  • Optimización de Cobertura (Sonar): El uso de DTOs generados automáticamente alivia la carga de mantenimiento y cobertura de pruebas. Dado que estas clases son código generado por herramientas estándar, se reduce la cantidad de componentes que SonarQube podría marcar como faltantes de cobertura, permitiendo al equipo enfocarse exclusivamente en probar la lógica de negocio real.
  • Validaciones embebidas: Las restricciones de tamaño, formato y nulidad definidas en el contrato se aplican automáticamente en el código generado.
  • Estandarización: Todas nuestras APIs tendrán la misma estructura y calidad de documentación.

4. Detalles Importantes

Para APIs RESTful, esta herramienta es super ventajosa porque:

  • Gestiona perfectamente la semántica de HTTP (códigos de estado, verbos, parámetros).
  • Permite usar el Delegate Pattern: el generador crea la interfaz y tú solo implementas la lógica de negocio en una clase separada, manteniendo el código generado limpio y desacoplado.
  • Facilita enormemente las pruebas de integración al tener clientes tipados.

5. Prerrequisitos para la Adopción

  • Herramientas Gradle o Maven configurado con el plugin org.openapi.generator.
  • Conocimiento Entender la especificación OpenAPI 3.0/3.1.
  • Proceso Definir el YAML como el artefacto que se versiona y lidera el cambio.
  • Librerías Dependencias necesarias en el proyecto (ej. jackson-databind-nullable, swagger-annotations, springdoc-openapi).

6. Configuración de Capas: Servidor y Clientes

A. Capa Controller (Spring Server)

Utilizamos el generador spring con el perfil de Spring Boot 3/4 y soporte para Jakarta EE. Configuramos el delegatePattern para mantener el código generado separado de la lógica.

// En build.gradle.kts
tasks.register<GenerateTask>("openApiGenerateServer") {
    generatorName.set("spring")
    inputSpec.set("$projectDir/src/main/resources/openapi.yaml")
    configOptions.set(mapOf(
        "delegatePattern" to "true",
        "useSpringBoot3" to "true",    // Compatible con Spring Boot 3 y 4 (Jakarta EE)
        "useJakartaEe" to "true",
        "documentationProvider" to "springdoc",
        "useBeanValidation" to "true",
        "interfaceOnly" to "false"
    ))
}

B. Capa Cliente (Java SDK)

Para la comunicación interna entre microservicios, generamos clientes ligeros usando la librería native (Java 11+ HttpClient) para evitar sobrecarga de dependencias.

tasks.register<GenerateTask>("openApiGenerateClient") {
    generatorName.set("java")
    library.set("native")
    inputSpec.set("$projectDir/../msa-task-mgmt/src/main/resources/openapi.yaml")
    configOptions.set(mapOf(
        "useJakartaEe" to "true",
        "dateLibrary" to "java8"
    ))
}

7. Uso Práctico y Mapeo de Dominio

Implementación del Delegate

El DelegateImpl inyecta el UseCase y el Mapper para transformar los datos:

@Service
@RequiredArgsConstructor
public class UserManagementDelegateImpl implements UserManagementApiDelegate {
    private final UserServicePort userServicePort;
    private final UserMapper userMapper;

    @Override
    public ResponseEntity<GetUserResponse> createUser(PostUserRequest request) {
        var userDomain = userMapper.toDomain(request);
        var savedUser = userServicePort.save(userDomain);
        return ResponseEntity.ok(new GetUserResponse()
                .data(userMapper.toDto(savedUser)));
    }
}

Consumo de Microservicios

El ExternalServiceAdapter envuelve el cliente generado para cumplir con el puerto de salida:

@Component
@RequiredArgsConstructor
public class TaskExternalServiceAdapter implements TaskExternalServicePort {
    private final TaskManagementApi taskManagementApi;

    @Override
    public List<Task> getTasksByUserId(Long userId) {
        var response = taskManagementApi.getAllTasks(null, userId, 0, 10);
        return response.getData().stream()
                .map(this::toDomain)
                .toList();
    }
}

8. Ejemplo de Configuración Completa (Gradle Kotlin DSL)

openApiGenerate {
    generatorName.set("spring")
    inputSpec.set("$projectDir/src/main/resources/openapi.yaml")
    outputDir.set(layout.buildDirectory.dir("generated/openapi").get().asFile.absolutePath)
    configOptions.set(mapOf(
        "delegatePattern" to "true",
        "useSpringBoot3" to "true",
        "useJakartaEe" to "true",
        "interfaceOnly" to "false"
    ))
}

9. Estandarización de Mapeos (MapStruct)

Para mantener el Dominio Puro, es obligatorio usar MapStruct para convertir entre DTOs generados y Entidades de Dominio. Esto evita que la capa de aplicación conozca los contratos externos.

@Mapper(componentModel = "spring")
public interface UserMapper {
    User toDomain(PostUserRequest dto);
    UserResponseDto toDto(User domain);
}
