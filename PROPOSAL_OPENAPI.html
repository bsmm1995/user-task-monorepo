Adopción de API-First con OpenAPI Generator

1. Introducción

Esta propuesta busca transformar nuestra forma de construir APIs RESTful, pasando de un enfoque basado en código (Code-First) a uno basado en el contrato (API-First). Utilizando OpenAPI Generator, podemos automatizar la creación de código repetitivo y garantizar la sincronía total entre microservicios.

2. Flujo de Trabajo Propuesto

  1. Generación del Contrato: Dado que actualmente no contamos con SwaggerHub ni con otra plataforma que permita gestionar de forma centralizada el ciclo de vida, versionamiento y gobernanza de contratos OpenAPI, adoptaremos un enfoque asistido por IA para la creación del contrato inicial. A partir de los requerimientos del negocio, generaremos el archivo openapi.yaml como punto de partida formal del diseño. Este contrato servirá como artefacto fuente para la evolución posterior del API y como base para la adopción del modelo Contract‑First dentro de la organización.
  2. Evolución del Contrato: El contrato se convierte en la "Única Fuente de Verdad" (Single Source of Truth). Cualquier cambio se discute y aprueba en el YAML antes de tocar código.
  3. Automatización (Build Time): Durante el proceso de compilación, el generador crea automáticamente:
    • Interfaces de Controladores (Server Stubs).
    • DTOs (Data Transfer Objects) con validaciones Jakarta/Bean Validation.
    • Clientes de API listos para usar (SDKs internos).
  4. Ingeniería Inversa (Legacy): Para servicios existentes, extraeremos los contratos desde /v3/api-docs para generar clientes de forma inmediata.

3. Ventajas Principales

🚀 Productividad

  • Cero DTOs manuales: Se acabó escribir clases repetitivas y sus mappers básicos.
  • Contratos inmediatos: Los equipos de Frontend y otros Microservicios pueden empezar a trabajar con el contrato antes de que la lógica esté implementada.
  • Reducción de errores: Se eliminan los errores de "typo" en nombres de campos o tipos de datos.

🛡️ Calidad y Consistencia

  • Garantía de Firma: Los clientes siempre consumen la versión exacta que el servidor expone.
  • Validaciones embebidas: Las restricciones de tamaño, formato y nulidad definidas en el contrato se aplican automáticamente en el código generado.
  • Estandarización: Todas nuestras APIs tendrán la misma estructura y calidad de documentación.

4. Detalles Importantes

Para APIs RESTful, esta herramienta es super ventajosa porque:

  • Gestiona perfectamente la semántica de HTTP (códigos de estado, verbos, parámetros).
  • Permite usar el Delegate Pattern: el generador crea la interfaz y tú solo implementas la lógica de negocio en una clase separada, manteniendo el código generado limpio y desacoplado.
  • Facilita enormemente las pruebas de integración al tener clientes tipados.

5. Prerrequisitos para la Adopción

  • Herramientas Gradle o Maven configurado con el plugin org.openapi.generator.
  • Conocimiento Entender la especificación OpenAPI 3.0/3.1.
  • Proceso Definir el YAML como el artefacto que se versiona y lidera el cambio.
  • Librerías Dependencias necesarias en el proyecto (ej. jackson-databind-nullable, swagger-annotations, springdoc-openapi).

6. Configuración de Capas: Servidor y Clientes

A. Capa Controller (Spring Server)

Para generar la capa de exposición (Controller), configuramos el generador spring. La clave es el uso de Interfaces y Delegates para separar el código generado de la lógica de negocio.

// En build.gradle.kts
tasks.register<GenerateTask>("openApiGenerateServer") {
    generatorName.set("spring")
    inputSpec.set("$projectDir/src/main/resources/openapi.yaml")
    configOptions.set(mapOf(
        "delegatePattern" to "true",   // Genera interfaces Delegate
        "interfaceOnly" to "false",    // Genera Controllers que llaman al Delegate
        "useSpringBoot3" to "true",    // Soporte para Jakarta EE
        "useTags" to "true"            // Organiza por tags del YAML
    ))
}

Cómo implementar: No modificas el Controller. Implementas la interfaz {Resource}ApiDelegate y Spring la inyecta automáticamente.

B. Capa Cliente (Java SDK)

Para consumir otros microservicios, usamos el generador java con la librería native (ligera, usa HttpClient de Java 11+).

tasks.register<GenerateTask>("openApiGenerateClient") {
    generatorName.set("java")
    library.set("native") // Sin dependencias pesadas de frameworks
    inputSpec.set("$projectDir/../otro-servicio/openapi.yaml")
    configOptions.set(mapOf(
        "useJakartaEe" to "true"
    ))
}

7. Uso Práctico y Llamada de Métodos

Implementando el Controller

Usando el Delegate Pattern, tu código queda limpio:

@Service
public class UserDelegateImpl implements UserApiDelegate {
    @Override
    public ResponseEntity<UserDTO> getUser(Long id) {
        // Tu lógica de negocio aquí
        return ResponseEntity.ok(new UserDTO().id(id));
    }
}

Invocando un Cliente

Llamar a otro microservicio es tan simple como usar un objeto tipado:

// 1. Configurar el cliente (una vez)
ApiClient client = new ApiClient().setBasePath("http://tasks-ms");
TaskApi taskApi = new TaskApi(client);

// 2. Llamar al método (con tipos reales)
TaskDTO task = taskApi.getTaskById(123L);
System.out.println(task.getName());

8. Ejemplo de Configuración Completa (Gradle)

openApiGenerate {
    generatorName.set("spring")
    inputSpec.set("$projectDir/src/main/resources/openapi.yaml")
    outputDir.set("$buildDir/generated/openapi")
    configOptions.set([
        delegatePattern: "true",
        useSpringBoot3: "true",
        interfaceOnly: "false"
    ])
}
